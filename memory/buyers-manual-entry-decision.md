Stakeholder feedback (2026-07-01) asked to enable manual data entry on the Buyers "revenue sheet" + "leads records section" and retire the "Add record" flow. Scope was confirmed as **just the record grids** (`RecordsSection` → `RecordsGrid`, used by both "Revenue billing" on the Buyers page and "Leads Record" on the Records page), NOT the per-buyer "Monthly Sheet" (`BuyersSheet`).

**Why:** In `RecordsGrid`, `counted` is a real, independently-stored column on `call_records`, so making it a free input (decoupled from answered+missed) was frontend-only and directly supports the two buyer categories — "Yes": counted = answered+missed; "No/Non-Missed": missed excluded. In `BuyersSheet`, answered/missed/counted/revenue are SQL SUM aggregates over call_records (see `BuyerController::index`) with no backing column, so manual entry there would need a backend + schema change — deferred.

**How to apply:** If asked to make the Monthly Sheet's answered/missed/counted keyable, that requires new stored columns on `buyers` (or writing a synthetic call_record) and touches dashboard/reports that aggregate call_records. Also: Average Rate (Total ÷ Counted) was added to the totals rows; the top "Add record" button in `RecordsSection` is commented out (records are keyed inline).

Follow-up (same day): buyer **rate** is now typeable per record in the grids (removed the `disabled={isBuyer}` lock in `RecordsGrid` existing + draft rows, and in `RecordForm`); the draft row gained a "+ New…" option that lets you **type a new buyer/campaign code** (find-or-create via `buyer_code`/`campaign_code` on the store endpoint, seeding the entity rate). Existing-row entity code stays read-only on purpose — it's the buyer identity, and renaming lives on the Monthly Sheet (`BuyerController::update` also has a notes-wipe footgun when notes aren't sent). Editing a buyer record's rate only changes that record; editing the master rate on the Monthly Sheet still propagates to all its records.

Follow-up 2 (same day): in the **buyer** draft row the "Destination" column dropdown is now commented out and replaced with a plain typing `Input` (find-or-create by code; auto-fills rate from a matching destination until the rate is keyed in manually).

Follow-up 6 (same day): the Buyers sheet excludes **weekends** (Sat/Sun) as non-working days. `BuyerController::index` join now includes `AND EXTRACT(DOW FROM r.record_date) BETWEEN 1 AND 5` (Postgres DOW 0=Sun..6=Sat → 1..5 = Mon–Fri), so no weekend record contributes to Total Calls Bought / Amount / average rate, and weekend dates don't count toward `record_days` (the Average-Calls-a-Day divisor). Scope = Buyers tab only; the Daily Sheet (raw data entry) and Dashboard/Reports still include all days. Backend-only change (no migration). Sort order note: Buyers tab + Daily Sheet grid now always sort by rate desc.

Follow-up 5 (same day) — SUPERSEDES the BUYERS portion of Follow-up 4 (campaigns unchanged): the buyers Monthly Sheet was redesigned to match a client screenshot. New columns: **Sr. No. · Buyers · Total Calls Bought · Average Calls a Day · Rates · Amount Received** (dropped Answered/Missed/Status/Replacement/actions/add-row). "Total Calls Bought" **always auto-derives** from the Daily Sheet records (`SUM(counted)` in the date range) via `BuyerController::index` — so it changes with the date range. It is **read-only** in the sheet (no override; the earlier `counted_override` idea was removed per the user because a pinned value didn't change across ranges). Buyers need NO stored total column. Only the buyer code + Rate are editable. Also: the "Leads Record" tab was renamed **"Daily Sheet"** (`Layout.tsx` nav label + `Records.tsx` title). Average Calls a Day = round(counted ÷ `record_days`) where `record_days` = COUNT(DISTINCT r.record_date) in range (N/A when 0 → e.g. override-only buyers with no records). Amount Received = rate×counted (read-only). Total row shows Average rate (revenue÷counted) under Rates + a "Total Average Calls a Day" bar (grand total ÷ max record_days). Rows auto-save on blur (no save/delete buttons). Buyers.tsx sorts by counted desc. Also fixed the `BuyerController::update` notes-wipe (now `notes = COALESCE(:notes, notes)`). Date filter drives the auto-derived totals. NOTE divergence: campaigns Monthly Sheet is still independent-editable (Follow-up 4) while buyers now auto-derive — not yet aligned.

Follow-up 4 (same day) — SUPERSEDES the "Monthly Sheet stays a computed rollup" decision above: the user chose to make the Monthly Sheets **directly editable**. Migration `006_editable_monthly_sheets.sql` adds stored `answered/missed/counted` to `buyers` and `campaigns` (+ `cost` on campaigns) and `replacement` to `call_records`, backfilled from current aggregates. `BuyerController::index` / `CampaignController::index` now read those stored columns instead of `SUM()`-ing call_records — so the Monthly Sheets are now an INDEPENDENT source from the Leads Records page + dashboard (which still aggregate call_records; the two can diverge). BuyersSheet: Code/Answered/Missed/Counted/Rate/Status editable, Total Bill auto = rate×counted. CampaignsSheet: Code/Answered/Missed/Counted/Total Bill(cost)/Status editable, Avg Rate auto = cost÷counted. Also added a **Replacement** column (buyer grids only, between Missed and Counted) — keyed in like Counted but display-only, never in totals. Retired: the "Add buyer"/"Add campaign" header buttons + their modals/forms (add inline on the sheet now) and the whole "Revenue billing" `RecordsSection` on the Buyers page (duplicated Leads Records). **DEPLOY: migration 006 must be run by hand on the VPS (migrations aren't auto-deployed) BEFORE the new backend loads, or buyers/campaigns endpoints 500 on the missing columns.**

Follow-up 3 (same day): applied full parity to the **Campaigns > Cost billing** section (same shared `RecordsGrid`). The `DraftRow` was refactored so BOTH the "Campaign" entity column and the "Source" (destinations) column are now typing `Input`s — all dropdowns/Selects commented out, `Select` import removed. `entityId`/`newSource`/`destOptions`/`onEntity`/`onSourceSel` and the client-side `createDestination` pre-create were dropped; the server (`RecordController::store` → `resolveId` + `sourceRate`) now handles find-or-create + linking the source with its rate. `onEntityType` (rate auto-fill only for buyers) and `onSourceType` (rate auto-fill from matching destination) drive the two fields. Existing campaign rows were already editable (source Input + rate); their entity code stays read-only like buyers.
